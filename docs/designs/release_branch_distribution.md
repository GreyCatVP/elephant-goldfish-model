# Release-branch distribution for the Claude directory

*   **Author:** [@n3wth](https://github.com/n3wth)
*   **Status:** Draft
*   **Date:** 2026-10-29

## Overview

The Claude directory scans a plugin folder in a GitHub repository. Today that
folder, `distributions/claude`, is generated by `scripts/pack_plugin.py` and
committed to `main`. This design stops committing it. When a maintainer publishes
a release, a workflow verifies the release's attested `egm-claude-<version>.zip`
and adds its contents as one commit to a generated branch, `release/claude`.
The directory tracks that branch.

## Problem Statement

A committed generated folder drifts from its source, and nothing in the
repository keeps it current. From the commit that added the folder to f0ba151,
`git log --oneline -- README.md .claude-plugin agents skills docs` lists 48
commits and `git log --oneline -- distributions/claude` lists 38.

`test_published_claude_runtime_is_current` compares every byte of the folder with
a fresh build. It runs on pull requests, so it catches drift only against a
`main` that is already stale. PR #208 ("docs: note Antigravity (agy CLI) also
requires /egm: prefix") changed `README.md` and merged without regenerating the
folder. The test now fails on `main` and on every open pull request, including
Dependabot's. PR #209 ("fix(packaging): sync the packaged readme") regenerates
the folder once. It does not prevent the next drift.

The Windows unit job runs the same failing test. The matrix uses the default
`fail-fast: true`, so Ubuntu's failure cancels Windows and the check reads
"cancelled" instead of "failed".

### Directory portal constraints

Source: Anthropic, [Submit your plugin](https://claude.com/docs/plugins/submit),
read on 2026-10-29.

*   The portal reads a GitHub repository, an optional plugin path (the folder
    that holds `.claude-plugin/plugin.json`), and an optional tracked branch or
    tag. It scans each new commit on the tracked branch or tag. It does not
    accept a ZIP for a directory listing.
*   An organization has one submission per repository and plugin path. The
    repository and plugin path cannot be changed after submitting. The tracked
    branch or tag can be changed in the plugin's settings.
*   If `plugin.json` sets `version`, it must be raised with every release.
*   The portal's Validate step run on 2026-10-29 against
    `google/elephant-goldfish-model`, plugin path `distributions/claude`, branch
    `main` at f0ba151, passed with 6 warnings and 9 policy holds. A policy hold
    sends a version to a reviewer. Nothing was submitted.

## Goals

1.  `main` contains no generated copy of the Claude runtime.
2.  The directory sees a new version only when a maintainer publishes a release.
3.  The files on `release/claude` are exactly the files of the release's attested
    `egm-claude-<version>.zip`. The workflow does not rebuild them.
4.  A pull request cannot fail because a generated folder is stale.
5.  Pull requests still fail if the runtime builder is broken.

Goals 1 and 4 hold after Phase 6 of the rollout. Until then the committed copy
and its test remain.

## Non-Goals

*   Changing the contents of the runtime or the OpenAI package.
*   Changing release attestation, `SHA256SUMS`, or the draft-release flow.
*   Submitting to the directory. A maintainer does that in the portal.
*   Resolving the portal's name, publisher, and icon policy holds.
*   Supporting hosts other than Claude on this branch.

## Open Questions

*   **Existing submission and layout** (gates Phase 4): Has anyone submitted this
    repository to the directory, from any organization or through the earlier
    Console form at `platform.claude.com/plugins/submissions`? The portal refuses
    a second submission for the same repository and plugin path from another
    organization, and the plugin path is fixed at the first submission. This
    design puts the plugin at the root of `release/claude`, so the plugin path
    stays empty. If a submission with plugin path `distributions/claude` exists,
    the branch layout must match it. The author's account has no submission for
    this repository.
*   **Portal scan timing**: How soon after a push does the directory scan the new
    commit? The portal documents a scheduled check and an optional push webhook
    but no interval, so release-to-listing latency is unquantified.
*   **Organization policy** (answered by Phase 4): Does an organization-level
    Actions policy limit `GITHUB_TOKEN` writes? The author cannot read that
    setting. A throwaway fork under a personal account pushed the branch with
    the same workflow, but a fork does not inherit the organization's policy.

## Critical User Journeys (CUJs)

### CUJ 1: Maintainer ships a release

*   **Given**: A release PR raised `version` in the manifests, a
    `vMAJOR.MINOR.PATCH` tag exists on `main`, and **Prepare draft release**
    (`release.yml`) produced a draft with attested ZIPs.
*   **When**: The maintainer reviews the draft and publishes it.
*   **Then**: The workflow verifies the Claude ZIP's attestation, extracts it, and
    adds a commit to `release/claude`. The directory scans that commit as a new
    version.

### CUJ 2: Contributor changes a source file

*   **Given**: An open pull request edits `README.md` or a skill.
*   **When**: The pull request is tested and merged.
*   **Then**: No generated folder needs updating. `release/claude` does not
    change until the next release.

### CUJ 3: Verification fails

*   **Given**: The release's Claude ZIP has no valid attestation from
    `release.yml` on `main`, or its manifest version differs from the tag, or the
    release is a draft or prerelease.
*   **When**: The workflow runs.
*   **Then**: The workflow fails before pushing. `release/claude` keeps its
    previous version, and the maintainer sees a failed run.

### CUJ 4: Publish an existing release by hand

*   **Given**: A release exists but `release/claude` lacks it: the branch's first
    publication, a release made before the workflow existed, a release published
    with `GITHUB_TOKEN`, or a push that failed.
*   **When**: A maintainer runs the workflow from `main` with the tag.
*   **Then**: The branch gains that release's commit. If the branch already holds
    identical content, the run reports that and changes nothing.

## Proposed Architecture

```text
publish release        verify and extract              release/claude         portal
---------------        ------------------              --------------         ------
release.yml built      gh attestation verify           one commit per         tracks the
and attested the  ---> unzip egm-claude-<v>.zip  ----> published release,    branch and
ZIP; maintainer        checks: tag, version, order     fast-forward   ------> scans each
publishes it                                           only                   commit
```

### Trigger

`.github/workflows/publish-claude-branch.yml` runs on `release: published`, and
on `workflow_dispatch` with a `tag` input for CUJ 4. A release event skips
prereleases. For both triggers the workflow checks that the tag matches
`vMAJOR.MINOR.PATCH`, that the tagged commit is an ancestor of `origin/main`
(this needs `fetch-depth: 0`), and that the release is neither a draft nor a
prerelease. A manual run must start from `main`, as `release.yml` requires.

A release event runs against the tagged commit, so only tags that contain the
workflow file trigger it. A release published by another workflow with
`GITHUB_TOKEN` does not trigger it. CUJ 4 covers both.

### Verify and extract

`release.yml` builds the runtime ZIPs on `main` and attests them with GitHub
artifact attestations. An attestation is a signed statement that a given
workflow run produced a given file. The release notes tell users to check it with
`gh attestation verify`.

The new workflow downloads the single `egm-claude-*.zip` release asset and runs
the same check with `--signer-workflow <repo>/.github/workflows/release.yml` and
`--source-ref refs/heads/main`. It then extracts the ZIP. It does not run
`pack_plugin.py`. The published bytes are the attested bytes, so the design needs
no assumption that the builder gives identical output on a different runner.

### Branch commit

`scripts/publish_runtime_branch.py` takes the extracted folder, the ZIP, the tag,
the source commit, and the remote. Its contract:

| Rule | Behavior |
|---|---|
| Inputs | Tag must match `vMAJOR.MINOR.PATCH` without leading zeroes. The commit must be 40 lowercase hex digits. Violations raise `ValueError`. |
| Archive | Every ZIP entry must pass its CRC check. The folder must hold the same paths and bytes as the ZIP, which catches extraction faults. |
| Manifest | `.claude-plugin/plugin.json` must exist in the folder, and its `version` must equal the tag without `v`. |
| Branch lookup | `git ls-remote --exit-code` exit 0 fetches the tip with `--depth=1`. Exit 2 starts an orphan branch. Any other exit raises `RuntimeError`. |
| Repeat | If the folder equals the branch tree the script returns without committing. This check comes first. |
| Order | A version below the branch's is refused. The same version with other content is refused. Versions compare as integer triples. |
| Commit | One commit as `github-actions[bot]`, subject `Release <tag>`, body `Source: <commit>`. The commit is the tag's commit as recorded by the release. |
| Push | `git push origin HEAD:refs/heads/<branch>` without force. A Git failure raises `RuntimeError` with Git's message. |
| Bytes | Every Git call runs with `core.autocrlf=false` and `core.safecrlf=false`, so committed bytes equal ZIP bytes on any platform. |

The tree of every commit is the ZIP's tree. The plugin sits at the branch root,
so its manifest path is `.claude-plugin/plugin.json`. Each commit stores a full
copy of about 250 kB, so history grows slowly.

### Failure handling and ordering

*   A failed verification, a version mismatch, an older version, a draft or
    prerelease, or a rejected push fails the job and leaves the branch unchanged.
    The maintainer fixes the cause and re-runs the job or runs the workflow by
    hand.
*   One concurrency group runs publishes one at a time and does not cancel a
    running one. GitHub keeps one running and one pending run per group, and a
    newer pending run replaces an older pending run. If two releases publish
    close together, the older may be skipped. Re-running the older tag is then
    refused by the older-version rule, which is the intended result.
*   Repeating a successful tag changes nothing.
*   There is no force push. A bad release is corrected by publishing a higher
    version.

### Security

*   The workflow sets `permissions: {}` at the top and grants `contents: write`
    only to the one job that pushes.
*   Actions are pinned by commit SHA as in the other workflows. The tag passes
    through an environment variable and is matched against a regular expression
    before use. The workflow uses no secrets other than the job token. The token
    reaches Git as a masked `http.extraheader` set through environment variables
    for one step, and checkout does not persist credentials.
*   The attestation binds `release/claude` to a ZIP that `release.yml` built on
    `main`. It does not bind the ZIP to the tag's commit, and `docs/releases.md`
    allows the attested source to differ from the tag. Anyone who can create a
    tag already has write access, so this design accepts that and relies on the
    tag ruleset below.
*   Not enforced: that only this workflow can push. GitHub rulesets restrict by
    actor, not by workflow. A maintainer with write access can push a normal
    commit to `release/claude`, and the portal scans it as a version.
*   Recommended settings, applied by a maintainer in Phase 3: a ruleset on
    `release/claude` that blocks deletion and non-fast-forward updates, and a
    ruleset on `v*` tags that limits who can create them. Today only the default
    branch has a ruleset and there are no tag rules.

### What stays on main

`scripts/pack_plugin.py`, `scripts/prepare_release.py`, and their tests. A pull
request still fails if the builder breaks through
`test_runtime_bundle_is_complete_and_reproducible` in
`tests/unit/test_packaging.py`, which builds both runtimes, and
`tests/integration/test_claude.py`. Neither compares against a committed copy.

## Alternatives Considered

### Alternative A: Keep the committed copy and regenerate it with a bot

*   **Pros**: The plugin path stays `distributions/claude` on `main`.
*   **Cons**: A bot needs permission to push to `main`, which the default-branch
    ruleset forbids without a bypass. If the portal tracks `main`, every bot
    commit becomes a scanned version. Parallel pull requests that change the same
    inputs conflict on the generated files.
*   **Reason for Rejection**: It adds write access to `main` and extra directory
    scans to solve a problem that disappears when the copy is not committed.

### Alternative B: Regenerate in a pre-commit hook

*   **Pros**: Local commits go out fresh. No server-side change.
*   **Cons**: It adds an install step for every contributor, and some will skip
    it. Today a failing test is the only prompt to regenerate the folder, and it
    has not prevented drift.
*   **Reason for Rejection**: CI must still catch what the hook misses, so the
    failure mode remains.

### Alternative C: Submit the repository root

*   **Pros**: Nothing to generate.
*   **Cons**: The directory scans the whole folder, including the website, tests,
    workflows, and contributor documents that the runtime package leaves out.
    Every merge to `main` becomes a scanned version.
*   **Reason for Rejection**: It changes what the directory reviews and lists.

### Alternative D: Upload the release ZIP, or track a tag

*   **Pros**: The ZIPs already exist and are attested.
*   **Cons**: The directory does not accept a ZIP. A tracked tag stays on its
    commit until the setting changes, and `docs/releases.md` forbids moving a
    tag, so each release would need a manual settings edit.
*   **Reason for Rejection**: A ZIP upload is not possible, and tag tracking
    adds a manual step per release.

### Alternative E: Rebuild from the tag and compare with the ZIP

*   **Pros**: A second, independent check of the attested ZIP.
*   **Cons**: It adds a second build path and assumes the builder gives identical
    bytes on a different runner image, which the repository tests only in one
    environment. A false mismatch would block releases.
*   **Reason for Rejection**: The attestation already ties the ZIP to the build
    that `release.yml` ran. The extra check adds a failure mode and no new
    guarantee.

## Risks and Mitigations

| Risk | Mitigation or acceptance |
|---|---|
| The nine policy holds keep a version from listing until a reviewer clears it. | Accepted. This design does not change them. |
| An existing submission uses a different plugin path. | Open Question 1 gates Phase 4. A wrong path after Phase 5 needs a new submission. |
| The portal's scan interval is undocumented, so latency is unknown. | Accepted. Measure it in Phase 5 and record it here. |
| A failed or rejected publish after a release is public leaves the directory on the previous version. | Accepted. The failed run is the signal, and no extra alert is added. Re-run the job. |
| A mistaken release reaches the directory. | Publish a higher version. There is no force push and no delete. |
| Someone with write access pushes a bad commit to `release/claude`. | The Phase 3 ruleset blocks force pushes and deletion. Ordinary pushes by writers are accepted. |
| The new tests have not run on a Windows runner against `main`. | The Tests workflow ran them on `windows-2025` in a fork and they passed. The first run on the real repository is the check. |
| Between Phases 4 and 6, `release/claude` ships a packaged `docs/releases.md` that still describes the committed folder. | Accepted. The next release after Phase 6 corrects it. |

## Rollout and Rollback

| Phase | Change | Gate before the next phase |
|---|---|---|
| 1 | Merge PR #209 so `main` is green. | Unit tests pass on `main`. |
| 2 | Merge the pull request that adds the script, its tests, and the workflow. | Tests and the repository's workflow scan pass. None of its files are packaged, so the freshness test is unaffected. |
| 3 | A maintainer adds the two rulesets above. | The rulesets are visible in the repository settings. |
| 4 | After Open Question 1 is answered, a maintainer runs the workflow by hand with the latest release tag. | `release/claude` exists with one commit, its tree equals the release ZIP, and the portal's Validate step passes on it. |
| 5 | A maintainer submits in the portal with tracked branch `release/claude` and an empty plugin path. | The portal accepts the submission for scanning. |
| 6 | One pull request deletes `distributions/claude` and the freshness test, and edits the documents listed in the Detailed Implementation Plan. | Unit tests pass. |

Phase 5 fixes the layout. Rollback for Phases 1 to 4 is to disable the workflow
and delete the branch. The branch is generated and holds nothing that is not in a
release. After Phase 5, recovery is forward only: publish a higher version. A
wrong plugin path needs a new submission. Restoring the committed folder after
Phase 6 does not restore the old listing, because the submission no longer
points at it.

## Detailed Implementation Plan

### Target Files to Create/Modify

#### 1. `scripts/publish_runtime_branch.py` (Create, Phase 2)

*   **Type / Scope**: Python script, standard library only.
*   **Proposed Changes**: `verify_archive(folder, archive)` and
    `publish(folder, tag, commit, remote, branch) -> bool`, following the
    contract table. The command line takes `--folder`, `--archive`, `--tag`,
    `--commit`, `--remote`, and `--branch` (default `release/claude`). It runs
    `verify_archive` and then `publish`, and prints `Published <tag> on <branch>`
    or `Already current: <tag> on <branch>`.

#### 2. `.github/workflows/publish-claude-branch.yml` (Create, Phase 2)

*   **Type / Scope**: GitHub Actions workflow, one job on `ubuntu-24.04`, using
    the runner's `python3`.
*   **Proposed Changes**: One job with these steps in order.

| Step | Behavior |
|---|---|
| Guard | Manual runs only: require `github.ref` to equal `refs/heads/main`. |
| Checkout | `actions/checkout` pinned by SHA, `fetch-depth: 0`, `persist-credentials: false`. |
| Resolve tag | Take `github.event.release.tag_name` or `inputs.tag` through `env`. Match the regular expression. Resolve the tag's commit. Require it to be an ancestor of `origin/main`. Write `tag` and `commit` to step outputs. |
| Download and verify | Require the release to be neither draft nor prerelease. `gh release download --pattern 'egm-claude-*.zip'`. Require exactly one file. `gh attestation verify` with the signer workflow and source ref. `unzip` to a runner temp folder. Pass the archive path on through `GITHUB_ENV`. |
| Publish | Build the base64 header from the job token, mask it, export it through `GIT_CONFIG_*` variables, and run the script with remote `https://github.com/<repo>.git`. |

The job has `permissions: {}` at the top level, `contents: write` on the job, the
job-level `if` that skips prereleases for release events, and one concurrency
group, `publish-claude-branch`, with `cancel-in-progress: false`.

#### 3. `tests/unit/test_publish_runtime_branch.py` (Create, Phase 2)

*   **Type / Scope**: Unit tests against a local bare repository. The workflow
    has no test beyond the linters and the manual run.
*   **Proposed Changes**: Each case asserts the remote is unchanged when it
    expects a failure.
    *   First release creates the branch with the bot author, subject, and
        `Source:` body, and no co-author line.
    *   CRLF and LF bytes survive.
    *   A later release fast-forwards, keeps the parent, and removes deleted files.
    *   Identical content publishes nothing.
    *   Unrelated history already on the branch is kept.
    *   `verify_archive` rejects changed, extra, and missing files, and a
        corrupted entry.
    *   `publish` rejects tags `1.2.3`, `v01.2.3`, and `v1.2.3;echo`, commit
        `abc`, a manifest version that differs from the tag, a folder without a
        manifest, a version below the branch's, the same version with other
        content, and a malformed version already on the branch.
    *   An unreachable remote raises `RuntimeError("git ls-remote failed")`.
    *   A `pre-receive` hook that rejects the push raises `RuntimeError("git push
        failed")` (skipped on Windows, which lacks a POSIX shell).
    *   A real build of the Claude runtime publishes with the manifest at the
        root.
    *   The command line publishes, repeats as a no-op, and exits nonzero on a
        tampered folder.

#### 4. `.github/workflows/tests.yml` (Modify, separate pull request)

*   **Type / Scope**: `jobs.unit.strategy`.
*   **Proposed Changes**: Add `fail-fast: false`. It has no dependency on the rest
    and can ship at any time. Check it by making one matrix entry fail on a
    scratch branch.

#### 5. Phase 6 changes (Modify or Delete)

*   **Type / Scope**: One pull request.
*   **Proposed Changes**:
    *   Delete `distributions/claude/`.
    *   In `tests/unit/test_packaging.py`, delete
        `test_published_claude_runtime_is_current`. `build` and `ROOT` stay in use.
        Check for unused imports afterwards.
    *   `docs/directory.md`: replace the first four sentences of the paragraph

    *   `docs/releases.md`: change step 2 to "Run `pytest tests/unit`. Include any
